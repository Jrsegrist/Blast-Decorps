# fe_0E7B0: hd_front_end 0E7B0.c (pfsHandler.c), the save thread fe_pak_thread (a loop that never returns).
# osRecvMesg / osSendMesg are modelled on the real queues (tools_port/models/mesgqueue.py): the thread
# takes the queued commands from gPakRequestQueue (messages in gPakRequestMesgs: cmd | arg1 << 8 | player << 16 |
# reply << 24), gPakRetraceQueue always "delivers", replies go to pakToGameMessageQ, and the run ends when the thread
# blocks on an empty command queue (or at the 60th osRecvMesg: a command that never settles loops).
# Memory (queues, globals) and the calls are compared, registers are not (the run stops mid-loop).
# gPreNmi stays 0 (otherwise the thread spins).

# random commands 0..24 (0, 23, 24: "Nonsense"), every result branch, game-mode bits, Yoshi window test
